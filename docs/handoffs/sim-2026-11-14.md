## 1. Planner bar loop (B36)
- Cause: in a guided run the runner replaces an action the guide refuses with `R.autoAction` (sim/lib/runner.mjs, `gfb`). Autoplay's first out-of-combat action is its own bar, which differs from template 1.2 (a Hunter: autoplay puts Mend Companion before Barbed Arrow). While the guide kept refusing the bot's map action, autoplay set slot 0 to `mend_companion`, the bot set it back to `barbed_arrow`, and so on. Nothing else changed, so the run never ended.
- Reproduction: on d9e607f with the ct50 scratch arm (contract XP × 0.5 in zone 1), seeds 1000-1299, the Hunter guided cells did not hit a refusal while the bar differed (0 stuck in 300 planner, 300 onebutton; 63 of 300 runs had one refusal with `--warmup 0`, none looped). The loop was reproduced exactly by forcing the guide's refusal of every zone 1 map action once the Hunter knows Mend Companion (seed 1003, planner and onebutton): the same slot 0 swap for ever.
- Fix (sim/lib/policy.mjs): `barGuard` in `makeBot`. A SET_BAR / SET_ITEM_BAR edit is not repeated until the state changes. The fingerprint is the serialized state without the spell and item bars, the content and the guide's hint counters (`tutorial.beats`, which change on every action). Once a held edit is reached the bot keeps the bar, the runner's fallback plays autoplay's next action, and the run goes on. Converging on a wanted bar never repeats an edit, so normal play is unchanged: the planner never needs the guard in classic, expedition or guided runs (test).
- Test: qa/sim/bar-guard.test.mjs. The forced-refusal run ends for planner and onebutton, the guard holds at least once, it holds a repeat and lets the edit through again after a state change, and the fingerprint ignores only the bars and the hint counters. The test fails without the guard (3 of 5).
