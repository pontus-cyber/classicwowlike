## How to run (on the demo build)

```
node tools/build.mjs --demo --out /tmp/demo.html
node qa/browser/demo/matrix.mjs       --file /tmp/demo.html          # about 2 min
node qa/browser/demo/reload.mjs       --file /tmp/demo.html          # about 3 min
node qa/browser/demo/fuzz.mjs         --file /tmp/demo.html --runs 5 # fuzz: pass = never reached
node qa/browser/demo/perf.mjs         --file /tmp/demo.html          # about 3 min
node qa/browser/demo/long-session.mjs --file /tmp/demo.html          # about 7 min; --speed 1 --max-runs 8 for the real-time pass, --speed 4 for fast
node qa/browser/demo/run-all.mjs      --file /tmp/demo.html
```

Browser matrix: the runner tries chromium, firefox and webkit and prints SKIP with the launch error for each it cannot start. Chromium stands for Chrome and Edge (Edge is Chromium-based; a real Edge row is a D.8 check on Windows). Firefox and WebKit run on a machine that has them (`npx playwright install firefox webkit`).
Sizes 1366x768 and 1920x1080; `--scale-row` adds 1920x1080 at 1.25 device scale as a report-only row. Ways of opening: `disk` (file://), `iframe` (a local http host page framing the build, sandbox "allow-scripts allow-same-origin"), `iframe-nosave` (sandbox "allow-scripts" only, so storage throws: the demo must show the 2.4 line "This browser window cannot save your progress." and play on; in the full build the cell only checks that the game plays on). Plain http on 127.0.0.1 is the stand-in for https (no certificate here); the ui-regress screens are the separate `ui-regress.mjs --file <build>`.
Long session: the 120 minutes are pace minutes (the summary's own autoplay estimate summed over runs), played at instant speed in one profile, at least 8 runs; on the demo it also checks that the hero cap (7) is reached and held.
Fuzz: half of the steps are the engine's autoplay choice, half random action types (MOVE, PASS_THROUGH, TAKE_ROAD, RING_BELL, FIGHT_BOSS, TRAVEL_ON, CHOOSE_NODE, LEAVE_HUB, ...) with ids from the zone view; the page refuses the illegal ones. `--expect full` (default for game.html) inverts the check: it passes only when zone 3 is seen, which proves the detector. The engine-level A2 (200 runs per class with `applyDemo()`) stays a Node test.

Frame time reading: this machine has no GPU and two CPUs. A blank full-window canvas fill runs at 16.7 ms here, so the sampler is sound, but the game's map costs about 150 ms a frame even unthrottled. `src/ui/app.js` redraws the scene on every animation frame (`scene.frame` in a loop that never stops), so a map that stands still still pays the full 1920x1080 canvas cost. The number is not a verdict on a real laptop with a GPU, and the 4x throttle on software rendering is not a usable stand-in here. D.8 on the owner's machine decides it; if the Lead wants a headless number, a redraw-only-when-dirty scene loop or a GPU runner is needed first. The check stays in the harness as written (limit 20 ms) and will fail on this machine until then.

## Findings

- BUG-QA-12 (major for the demo, open): the profile is stored at zone and Camp arrival and by END_RUN, the summary's button. F5 or closing the tab on the run summary loses what the run paid (Legacy, last zone's XP, the welcome, the guide counting as done); nothing is paid twice, but spec 5.3 calls the run end a checkpoint. Needs a decision: store at run end, or word 5.3 as "stored by the button".
- BUG-QA-13 (minor, open): DOM nodes grow by about 130 per run in a long tab (detached nodes and listeners); heap 1.18-1.29x.
- The frame loop above (not filed as a bug; a measurement question).
