## 2. What changed

- `src/engine/heat.js` `heatTime(s, t, why, at)`: the summary counts each toll on the Dimming clock of `at`, by default the player's node. `src/engine/nodes.js` `addTime(s, ev, t, why, from)`: `moveTo` (a walk) and `passThrough` pass the node of departure. The meter's reading when a walk's or a pass's toll starts is now the state it counts in. A node's own tolls are unchanged: they count on the clock of the node entered, its `pays` state first. Services, Grind waves, the Bell and Dimmed encounters count where the player stands. The Road counts by the run clock alone (rules 1.7.4). Nothing else in a run changes. Only `stats.heat.timeByState` (and the summary's copy) moves between states. Its total is still the run's tolls.
- Golden hashes: qa/engine s18 (150 hashes), s23 (6) and s28 (16) now hash the run with every `timeByState` masked to its total (`qa/engine/helpers.mjs` `tollsMasked`). Each was re-recorded on 57923eb with the engine before the change, and the changed engine hashes the same. This shows that no action, event, state or summary field other than the tolls by state differs, in any arm of those tables.
- `src/ui/heat.js` `meterReading(hv, H)` and `segmentAt(x, H)`: one reading of `heatView` gives the state's name, its line, the lit segment, the player's marker (`bar.marker`), the Dimming's diamond and `setter`, the marker of the clock that sets the state. The meter's `update()` draws only from it. Behaviour and look are unchanged. Before, it read the same fields in three places.
- docs/ARCHITECTURE.md: rows of src/engine/heat.js and src/ui/heat.js, and the Heat locator row.

Spec wording for the designer (engine choice, to confirm): rules 1.7.4 says "every toll spent counts in the state it starts in". The engine now reads that as follows: a walk's or a pass's toll starts on the node walked from, and a node's tolls start in the node entered. A sentence in 1.7.4 would make this explicit. DECISIONS row suggested: "Tolls by state: a walk's or a pass's toll counts on the Dimming clock of the node walked from (the meter's reading when it starts)".

## 3. For the designer: what the player would need to see (draft; rules unchanged)

All four rest on data the engine already gives; none needs a rule change.

1. **Which clock sets the Furnace** (item 1). The line drops the tolls figure when the Dimming sets the state, and the pointer the player reads stays on the run clock. Options: (a) keep the figure on the line: "Smouldering · The Dimming is near · 23 tolls to spare"; (b) when `by` is `dim`, draw the diamond as the main pointer and the run pointer as the secondary one; (c) a step's tooltip says when it changes the state, from `heatPreview` `change`, `state`, `by` and `dimIn`: "Costs 1 toll. The Furnace turns Smouldering: this node dims in 3 tolls." Today the tooltip only says "Costs 1 toll." (D150).
2. **What a node counts as** (item 2). Inside a node the meter reads the state after the node's tolls, but the node pays and counts in its entry state. `heatView.node.state` holds the entry state; the D150 pay line was dropped. When it differs from the meter, a line such as "This node counts as Calm (entered Calm)" would explain the summary's "9 Calm". The summary card could add: "A node's tolls are spent when you enter it."
3. **What a node costs in spread** (item 3, tester's top change 2). In a node's tooltip: "The Dimming takes up to N places while you are inside" (N = the nodes whose `dimAt` falls in the node's tolls, at most DIM_MAX_PER_TOLL × its tolls). This is a pure read the engine can add to `heatPreview` (for example `dims`: the node ids) once approved. `mapView.dim` already gives `count`, `total`, `maxPerToll`, `nextIn` and `nextCount` for the panel.
4. **The carry on arrival** (item 4). On arrival in a zone, one line from `heatView.carry`: "Zone 2 adds 20 tolls; you saved 10 before it: 30 to spare." Today it is only in the meter's tooltip (`carryLine`).

## 4. How to test

- `node --test qa/engine qa/rules qa/docs qa/sim qa/ui`: **1026 tests, 1026 pass** (1016 before; new: qa/engine/s29-heat-state.test.mjs 6, qa/ui/heat-state.test.mjs 4).
- qa/engine/s29-heat-state: a pass from a Smouldering node to a Calm one counts Smouldering, and the meter reads Calm after it. Over autoplay runs, every action's first toll counts in the meter's state before it (a node entered: its `pays`; the Road: the run clock). The summary block adds up. The rules as written are pinned: state = the hotter clock, the run marker = the heat, at most DIM_MAX_PER_TOLL places a toll (a Dungeon up to 10, a Quest up to 6), and tolls to spare on arrival in zone 2 = line(2) less the run's tolls, by Road or Bell. Both arms (Legacy on: legacy, oruvathLegacy, economyV2; off). The first two tests fail on 57923eb.
- qa/ui/heat-state: whole bridge runs (Hunter, Legacy on and off). On every view, the line names the state of the lit segment, and the setting marker lies in that segment. The run marker is `bar.marker`, and the diamond lies in `stateDim`'s segment. The summary's tolls by state are the engine's, and each walk's or pass's toll lands in the state the meter showed before it. The second test fails on 57923eb.
- ui-regress part I (the Furnace) alone at 1366x768: **30/30 pass**. Parts S and X at 1366x768: 69/70. The failing check, X-setout ("Set out shows the zone map within 250 ms": 309-357 ms here), also fails on an unchanged build of 57923eb on this machine. It is a timing check outside this change.
